# Clinic release candidate — 23 October 2026

## Scope

This release adds reconciled financial reporting and fixes inconsistent marketing conversion counts. It preserves existing roles, billing/payment/approval rules, synthetic demo separation and patient records. It does not create the first clinic owner or enable mail, payment, reminder, scanning or offsite-backup providers.

- `reports/financial`: daily, ISO-week (Monday start), monthly, service, provider, department, expense-category and cost-center grouping; optional period/dimension filters. The same applied filters are used for CSV/PDF/XLSX export. Export includes calculation definitions, filters and data-coverage metadata.
- Values use integer baisa during aggregation/allocation. Payments and refunds are apportioned once over current session links, with an explicit unallocated remainder and deterministic residual-baisa handling. General expenses are not silently assigned to a practitioner/service or added again to frozen overhead.
- Invoice creation, below-floor approval and package-sale paths now record issue-day/service/department facts atomically. Session approval records its day once. These are additive tables in the existing startup migration, on both SQLite and PostgreSQL. Existing records are not assigned invented historical dates.
- Marketing journey, summary and campaign conversion counts share one calculation. A linked booking counts once; unlinked legacy manual `Converted` records are separately identified and included once.
- The financial endpoint requires BOTH `finance.view` and `reports.view`; export additionally requires BOTH export grants. Assigned patient/provider scope cannot be widened by filter input. The explicit endpoint/audit inventory includes the new route.
- Attachment lists show scan state; files without a clean scan remain unavailable. The optional operator-controlled HTTPS scanner complements the local ClamAV socket and works without moving hosting. Any unavailable/invalid response, wrong content digest or post-scan content change fails closed.
- Next.js is pinned to **16.4.1**, fixing advisories reported for 16.4.0 (GHSA-2464-fhr4-w9xw, GHSA-p3m5-59mp-jv5r, GHSA-673q-mjm6-r5xr). The production dependency audit is rerun for this candidate.
- The synthetic backup harness now waits for PostgreSQL's final TCP listener rather than its temporary initialization socket. A separate self-contained test restores the full clinic schema and accesses the actual authenticated report and protected attachment from the restored database.

## Report interpretation and data limits

Collections/refunds use their transaction day in Asia/Muscat. Invoice values and current receivables are grouped by recorded invoice issue day. Frozen session costs use approval day. Undated legacy entries appear under `غير مؤرخ` without a period filter and are excluded from dated periods; coverage counts remain visible. Legacy invoice `paid` amounts unsupported by payment history are identified as a reconciliation difference and are not manufactured into transactions.

The report uses current invoice values, discounts and session allocations. It is **not** a historical as-of receivables ledger. The displayed collection-less-session-cost difference is a contribution comparison, **not certified accounting net profit**. Unknown service/department/provider attribution remains explicit. Incomplete frozen costs are flagged. Finance staff must approve these definitions and provide missing historic evidence before treating figures as final accounting statements.

## Reproducible isolated checks

Use Node 22 and installed development dependencies. Never point acceptance scripts at production.

```sh
npm test
CLINIC_TEST_POSTGRES=1 DATABASE_URL=<disposable-loopback-postgres> npm test
CLINIC_SECURITY_ACCEPTANCE=1 npm run test:audit
npm run test:ui-language
npm run test:backup-postgres
npm run test:financial-recovery
npm run lint
npm run format:check
npm run build
```

`test:financial-recovery` creates its own temporary PostgreSQL container, databases, key, encrypted archive and local application. It accepts no source/restore database URL. It checks corrupt-ciphertext rejection, restored financial results and byte-identical protected attachment access, then cleans up. This is a small synthetic recovery exercise, not evidence of production-scale RPO/RTO or offsite transfer.

## Initial deployed scope and operator activation

Current hosting stays on the existing Vercel project. The initial scope uses manual recorded payments and in-app workflows. No live external email/reminder/payment channel is claimed. Unscanned attachments may be stored in quarantine; they cannot download. No scanner endpoint or key is supplied by this release.

For the HTTPS scan adapter, privately configure `CLINIC_SCAN_ENDPOINT` (HTTPS, no URL credentials, redirects refused) and `CLINIC_SCAN_KEY` (at least 32 characters). The app POSTs raw bytes, `Authorization: Bearer ...` and `X-Content-SHA256`. Within 10 seconds the adapter must return HTTP 200 JSON `{ "state": "Clean" | "Infected", "sha256": "<matching digest>" }` with a response at most 4096 bytes. Only the selected operator/provider receives files. Validate the provider's storage/privacy/signature-update policy, then rescan quarantined files with `node scripts/scan-attachments.mjs`. The in-process synthetic scanner is a test fixture, never a production configuration flag.

Email remains unconfigured until the company chooses a provider/sender. Offsite transfer and retention pruning remain inactive until the company identifies its backup storage and approves retention/recovery objectives. Existing backup scripts and systemd examples are preparation for a separately configured operator environment, not proof of a Vercel backup schedule. Do not copy VPS deployment settings into the current hosting or activate a destination by guesswork.

Before clinical operations: owner bootstrap by the owner, approved staff roles/prices/clinical templates, migration/backup verification, clinic UAT and training/sign-off. Optional integrations do not prevent deploying the tested software with explicit safe limitations.
