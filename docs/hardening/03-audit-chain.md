Task 3: tamper-evident audit history
- Application writes append through one hash-chain writer. There is no public audit mutation endpoint. Each SHA-256 link covers previous hash, ID, actor, action, entity, before/after and timestamp; a separate state row records the head/count. PostgreSQL serializes only the audit writer using a transaction-scoped lock. Writes and links roll back together.
- Existing history is baselined once; legacyCount identifies how many pre-chain records were accepted at migration. This does not prove the authenticity of old history. Verification does not initialize/baseline untrusted history.
- Owner-only GET /api/audit/verify reports the first broken ID/reason. `node scripts/verify-audit.mjs` prints verification JSON and exits nonzero on failure. CLINIC_AUDIT_EXPECTED_HEAD optionally supplies an independently retained expected head.
- A database administrator can delete or replace audit, links and state, or recompute the chain. Application append-only behavior and hash chaining do not prevent this. Export the verified head/count periodically to an independently controlled append-only/WORM or signed external ledger; provider, schedule and retention need owner decisions. An old head alone requires verifying the retained checkpoint at that position, not comparing it to a newer head.
- Verified: 144/144 tests on SQLite + disposable PostgreSQL 17, zero skips; hash modification/deletion, legacy baseline, rollback and external-head mismatch tests added. HTTP acceptance passed (80 read routes/80 export attempts, five downloads, 141 no-grant entries, reset/security checks).
- Not verified: external anchoring, live database roles, production scale or a hostile database administrator. No production services contacted.
