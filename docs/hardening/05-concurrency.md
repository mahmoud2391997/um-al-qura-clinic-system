Task 5: row-level concurrency with a reversible rollout barrier

- Converted appointment booking/status/package deduction, stock movement, invoice/payment/discount and cash-close HTTP mutations now hold a shared migration barrier and acquire the relevant record/resource locks. Unconverted handlers hold the exclusive barrier, so legacy writes cannot race converted paths. This preserves safety while allowing converted mutations to run concurrently. Set CLINIC_POSTGRES_GLOBAL_LOCK=1 to restore the original full exclusive clinic lock.
- Provider/room, idempotency-key, hashed phone and cash-day resource rows handle absent-row races. Inventory/package/invoice/device/clinical records use FOR UPDATE. Phone lock keys contain a digest rather than raw contact data. Quick booking records patient audit events only after allocation locks are acquired, avoiding an audit/record lock-order inversion. Resource-lock schema is initialized under the existing migration lock.
- Independent-connection tests prove overlapping bookings admit one, repeated request IDs return one appointment, the last package session is used once, FEFO issues cannot make stock negative, concurrent collections cannot exceed the invoice, and cash closure reconciles accepted cash.
- Executed real parallel HTTP tests against a disposable PostgreSQL schema with the shared/row mode enabled: provider/room conflict, booking idempotency, one package deduction, stock remaining 3, invoice paid 60 of 100 and one cash closure. A separate PostgreSQL test checks ShareLock versus ExclusiveLock and verifies the rollback flag.
